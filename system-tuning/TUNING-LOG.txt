 [1] PAGEFILE -- fixed commit-limit exhaustion
-------------------------------------------------------------------------------
 PROBLEM   16 GB RAM + only a 1 GB pagefile = 16.71 GB commit limit, with just
           4.76 GB free while WSL2 is configured for 12 GB + 4 GB swap. WSL
           spinning up could exhaust commit -> allocation failures, not just
           slowdown.

 BEFORE    AutomaticManagedPagefile = True
           C:\pagefile.sys  system-managed, 1024 MB allocated
 AFTER     AutomaticManagedPagefile = False
           C:\pagefile.sys  InitialSize 4096 MB / MaximumSize 16384 MB

 NOTE      *** REQUIRES A REBOOT to actually resize the file. ***
           The registry entry is durable immediately; the file is not.

 REAPPLY (elevated PowerShell)
   $cs = Get-CimInstance Win32_ComputerSystem
   Set-CimInstance -InputObject $cs -Property @{AutomaticManagedPagefile=$false}
   $pf = Get-CimInstance Win32_PageFileSetting
   Set-CimInstance -InputObject $pf -Property @{InitialSize=4096; MaximumSize=16384}

 VERIFY
   Get-CimInstance Win32_PageFileSetting | Select Name,InitialSize,MaximumSize
   (Get-ItemProperty 'HKLM:\SYSTEM\CurrentControlSet\Control\Session Manager\Memory Management').PagingFiles
   EXPECT: C:\pagefile.sys 4096 16384

 REVERT
   Set-CimInstance -InputObject (Get-CimInstance Win32_ComputerSystem) `
     -Property @{AutomaticManagedPagefile=$true}

 [2] MAX PROCESSOR STATE -- removed artificial 99% frequency ceiling
-------------------------------------------------------------------------------
 PROBLEM   Max processor state on AC was 99%. Windows default is 100%; 99% is
           the legacy trick used to suppress Turbo Boost. On Alder Lake with
           HWP it does not fully disable turbo, but it hands the scheduler a
           ceiling that should not be there.

 BEFORE    PROCTHROTTLEMAX  AC = 0x63 (99%)   DC = 0x50 (80%)
 AFTER     PROCTHROTTLEMAX  AC = 0x64 (100%)  DC = 0x50 (80%)  <- DC unchanged

 SAFETY    No added thermal risk. PL1/PL2 (item 9) are the real governor of
           power draw; this only removes a frequency cap sitting above them.
           Measured effect: peak all-core went to 3529 MHz.

 REAPPLY (elevated)
   powercfg /setacvalueindex SCHEME_CURRENT SUB_PROCESSOR PROCTHROTTLEMAX 100
   powercfg /setactive SCHEME_CURRENT

 VERIFY
   powercfg /query SCHEME_CURRENT SUB_PROCESSOR PROCTHROTTLEMAX
   EXPECT: Current AC Power Setting Index: 0x00000064

 REVERT
   powercfg /setacvalueindex SCHEME_CURRENT SUB_PROCESSOR PROCTHROTTLEMAX 99
   powercfg /setactive SCHEME_CURRENT

 PL1 = 35 W   (sustained)
 PL2 = 60 W   (burst)

 These live in firmware, so nothing in Windows will reset them. They are the
 real governor of CPU power -- item [2] above only removes a frequency ceiling
 sitting above these limits.

 MEASURED BEHAVIOUR (all-core load, 2026-09-13, after item [2]):
   t=11-17s   3147 MHz   <- PL2 window, 60 W
   t=22-32s   2400 MHz   <- tau decay
   t=37-52s   1810 MHz   <- PL1 steady state, 35 W
   peak seen  3529 MHz
 Textbook PL2 -> PL1 staircase. Roughly a 20 s burst window. Costs about
 15-20% sustained multicore vs the stock 45 W PL1, in exchange for much lower
 temps and fan noise.

 INTEL DTT NOTE: the core DPTF / Innovation Platform Framework stack is
 HEALTHY (Processor Participant, Thermal Zone and 3 Generic Participants all
 report OK). Only "DTT Device Extension Component", a software shim, is in an
 error state. Dynamic thermal management is working. Static PL1/PL2 and DTT
 coexist -- the PL values set a ceiling low enough that DTT rarely intervenes.

 RECONSIDER PL1 WHEN THE ARC dGPU IS RE-ENABLED. With both CPU and GPU sharing
 one heatpipe budget, a hard 35 W CPU floor can starve whichever side is doing
 real work. Suggest raising PL1 to ~40 W and letting DTT arbitrate.

 [19] PIN GPU DRIVERS vs WINDOWS UPDATE            (new, 2026-10-06)
-------------------------------------------------------------------------------
 PROBLEM  Windows Update re-offers an older WHQL Intel graphics driver and
          overwrites the newer one installed manually from intel.com -- for BOTH
          Iris Xe (PCI\VEN_8086&DEV_46A6) and Arc A370M (PCI\VEN_8086&DEV_5693),
          which share one Intel package. DSAService/DSAUpdateService are already
          disabled (4.6b), so Windows Update is the only remaining pusher.
 CHOICE   GLOBAL exclude (recommended): WU stops delivering ANY driver; manual
          installs always work; no risk of stranding a GPU on Microsoft Basic
          Display Adapter (Code 48). Quality/security/feature updates unaffected.
 AFTER    ExcludeWUDriversInQualityUpdate = 1
            HKLM\SOFTWARE\Policies\Microsoft\Windows\WindowsUpdate
          SearchOrderConfig = 0   (never auto-fetch drivers from WU)
            HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\DriverSearching
 ORDER    Install the wanted Intel driver + REBOOT first, THEN run the script.
 LEAKED   Global alone was NOT enough: after applying it, Windows Update STILL
          downgraded the Iris Xe (DEV_46A6) back to 30.0.101.1329. Global keys
          are WU-preference level and WU's servicing stepped around them. The
          Arc (DEV_5693) held. Conclusion: on Home, use the per-device deny.
 HARDLOCK 2026-10-06: re-installed 32.x, rebooted, then applied per-device
          DenyDeviceIDs on BOTH GPU IDs (Retroactive=0). That is install-level
          enforcement -- "takes precedence... the device cannot be installed" --
          which WU cannot bypass. WU's catalog still LISTS the old driver, but
          any install attempt is refused ("forbidden by system policy").
 MANUAL   update workflow:  -LiftPerDevice  ->  install + reboot  ->  -IncludePerDevice
 HIDDEN   2026-10-06: the deny blocks INSTALL but WU still LISTED the drivers
          ("will install with the next cumulative update"). Also HID them so the
          WU list is clean, via PSWindowsUpdate (elevated):
            Install-Module PSWindowsUpdate -Force -Scope AllUsers
            Hide-WindowsUpdate -Title 'Intel*' -Confirm:$false
          Un-hide:  Show-WindowsUpdate -Title 'Intel*' -Confirm:$false
          A NEWER driver you actually want has a different title, so it is NOT
          hidden by this. Net: 3 layers = global exclude + per-device deny + hide.
 REAPPLY  pin-gpu-drivers.ps1 -IncludePerDevice     (global + per-device)
 VERIFY   (Get-ItemProperty 'HKLM:\SOFTWARE\Policies\Microsoft\Windows\WindowsUpdate').ExcludeWUDriversInQualityUpdate -> 1
